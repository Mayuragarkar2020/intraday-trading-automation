# Setup lifecycle, selection and database guarantees

[ASSUMED: proposal] Future paper contract only. No SQL migration or application code is executed by this design. The event journal is authoritative per D-015; relational constraint tables and JSON/UI projections are derived and transactionally maintained.

## Durable identity and transitions

[ASSUMED: proposal] Common event envelope E: event_id, account_id, IST session_date, setup_id, confirmation_id/attempt_id when relevant, instrument security ID+ISIN+NSE symbol, state_before/after, expected_sequence, event_at, known_at, recorded_at, reason, universe/pool revision, rule/config hashes, source receipt IDs/hashes and request_id. Reject reused idempotency key with changed payload. Include human actor, proposal/override and evidence provenance; no secret fields.
[ASSUMED: proposal] Setup ID hashes instrument+session+range-bar IDs+rule version; each confirmation is a distinct attempt. A symbol has at most one active arm per account; manual reselection creates a linked new attempt and never rewrites an old cancelled event.
[ASSUMED: proposal] The table's field column is additional to E. Restart means replay the committed event prefix, verify hashes/sequence, reconstruct projections, then apply the named behavior. In-memory states never authorize a fill.

INVALIDATED_STOP_TOUCHED differs from expiry; never call a filled position cancelled.

## Selection, shelf life and invalidation

[ASSUMED: proposal] Show entry/SL proposal, tick/source timestamp, proposed limit, cost model, risk budget, preview maximum quantity and readiness hold. Accept optional override T/S and selection reason; preserve original plus override without silently changing the user's prices. Risk preview is not final trigger-time quantity.
[ASSUMED: proposal] Server validates Decimal finite positive prices, exact tick multiples (reject, do not silently round override), 0<S<T, eligibility/final universe, reviewed session, setup TTL, quote receipt age<=5 seconds and latest validation candle close age<=90 seconds (range age is governed separately by setup TTL). Unknown quote/tick or live-price already crossing T rejects STALE_OR_ALREADY_BROKEN; do not interpret selection as an immediate market entry. Confirmation can arm only a still-valid setup.
[ASSUMED: proposal] Shelf life: 15 minutes from detected close, bounded by session cutoff; do not extend by repeated alerts or retries. Continuing independent setup detection can create a new revision; it never silently replaces an existing user's arm or entry/SL. At each interval reevaluate invalidation before trigger; low<=confirmed S cancels/invalidates before breakout. Invalidated stock gets no automatic replacement.
[ASSUMED: proposal] Missing five-minute bar, source revision, identity/eligibility failure, changed reference config, or a now-nontradable stock holds all new actions for that instrument. If no fill, cancel with explicit reason; if filled, transfer to visible recovery/protective management.
[ASSUMED: proposal] Double-tap: account+client_request_id uniquely maps canonical confirmation payload to result. Reuse identical request returns original confirmation/arm; changed payload conflicts. Concurrent confirmations lock session before allocating slots. Replacement requires explicit cancel+new request and fresh validations; cannot evade daily fill state.

## Relational invariants and atomic transaction

[ASSUMED: proposal] Future tables: paper_events (authoritative append-only), paper_session_control, paper_arm_slots, paper_order_attempts, paper_account_projection, paper_alert_outbox. Every primary write shares a session lock, server-pinned account and fencing epoch; migrations/roles protect direct inserts.
[ASSUMED: proposal] Enforce daily entry in the authoritative journal itself with a UNIQUE partial index on (account_id,session_date) WHERE event_type='ENTRY_FILLED' AND ledger_kind='PRIMARY'. A primary fill event carries positive q, BUY side, limit/fill/stop/risk/cost and must satisfy validated constraints. Shadow events have a distinct ledger kind/key.
[ASSUMED: proposal] Five-arm cap: paper_arm_slots has CHECK(slot BETWEEN 1 AND 5), PRIMARY KEY(account_id,session_date,slot), UNIQUE(account_id,session_date,confirmation_id) and unique active symbol. Only rows for active arms live there; history stays in events. Session_control locks plus no-fill-state guard reject inserts after fill; a DB trigger/constraint-backed session gate verifies this too, not just UI code.
[ASSUMED: proposal] There is one pending primary candidate per session_control row; it reserves entry evaluation but does not consume the daily fill. Armed candidate resolution must be known complete for all active arms in that interval. Earliest qualifying close wins; same-close highest frozen twenty-day traded value; exact tie ascending security ID as deterministic final fallback, recorded with tie-policy version.
[ASSUMED: proposal] Within ONE database transaction: lock session -> verify candidate/expected sequence/receipts/cash/risk -> insert unique ENTRY_FILLED event -> append ENTERED/MANAGED -> cancel all other active arms with SUPERSEDED_BY_FILL -> clear all slots/pending candidates -> update account/session projections -> write entered/cancelled outbox messages -> commit. No external Telegram call inside transaction.
[ASSUMED: proposal] Any SQL/cancellation failure rolls back the entire simulated fill and all other effects; no fill event survives without cancellations/manager. If outcome of commit is uncertain, stop entries, query idempotency key under lock, and reconcile before retry. Telegram delivery failure leaves committed cancellations intact and visible as ALERT_UNDELIVERED; it cannot resurrect arms.
[ASSUMED: proposal] A GAPPED_THROUGH winner cancels only that attempt atomically, frees candidate slot and logs zero fill. Other arms can compete in a later complete interval. No instant same-interval fallback or auto-rearm.
[ASSUMED: proposal] On restart with several arms: replay events, check slots/session projection/unique fill, apply wall-clock expiry/cutoff, inspect fresh eligibility, then resume prospective candles only. Missed historical breakouts remain missed/shadow, not new primary entries. If a fill already exists, any leftover arm projection is repaired/cancelled from authoritative events before engine resumes.

## Migration and PostgreSQL concurrency test design

[ASSUMED: proposal] Migration is future work requiring separate approval before production: create versioned empty tables/indexes/roles; audit old ledger hashes/cash/exposure; do not fabricate historical source verification. Map existing immutable events only with deterministic versioned adapter and provenance; otherwise retain legacy read-only account. If any open/unknown position or conflicting daily fills exists, block migration/entries and require reconciliation. No silent event rewrite, projection override or clearing daily history.
[ASSUMED: proposal] Future PG race test: two independent DB connections/processes, barrier before interval resolution, two valid armed stocks with known ADV and same close, reverse arrival and repeat after restart. Assert exactly one primary ENTRY_FILLED and correct highest-ADV winner; all others SUPERSEDED_BY_FILL, no remaining arm slots, one daily cash debit and matching outbox events. Attempt direct duplicate fill SQL: unique-index violation proves DB guarantee. Another test concurrently arms six distinct stocks; only five commit; late arming after fill rejected by DB gate.
[ASSUMED: proposal] Fault tests inject failure after fill event insertion, during other-arm cancellation, projection update and outbox insert: each leaves either all committed or no fill/cancellations. Retry/serialization/deadlock handling must revalidate complete interval, not pick arrival winner. These are test designs, NOT RAN_TEST.
